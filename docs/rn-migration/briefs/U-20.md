## Shape

- `src/data/api/http.ts`: one `apiRequest()` that reads the base URL from `EXPO_PUBLIC_API_URL`
  (default `http://127.0.0.1:8787`), sends JSON, attaches the access token, parses every response
  with the contract schema from `@coachcal/api-contract` (a 2xx body that fails the schema is a
  server error), turns the error envelope into a typed error, and on 401 refreshes the session once
  and retries once.
- `src/data/api/scanClient.ts`: the `CoachCalApi` interface (`analyzeFood(request)`), `LiveScanApi`
  (`POST /v1/scan`), and `ScanApiError` with the three helpers of the Swift enum. An optional
  telemetry callback reports tier (`tier2` after 5 s) and duration, like `LiveApiClient`.
- `src/testing/fixtureScanApi.ts`: the port of `FixtureApiClient` and `FixtureModels`: scenario by
  name (from the `--ccScanScenario` launch argument, which `src/debug/launchArgs.ts` will provide
  later: for now take the scenario name as a constructor argument), the golden files under
  `packages/api-contract/golden/`, and `scan-response-200-unresolved.golden.json` read from
  `native/App/CoachCal/Resources/Fixtures/` (copy its content into `src/testing/fixtures/`).
- `src/data/api/syncClient.ts`: same wire behavior, but the bearer token comes from an injected
  `() => Promise<string | null>` provider; the default provider keeps today's dev-token behavior so
  `src/data/sync/runtime.ts` and `src/data/binding.ts` compile and pass unchanged. After a push,
  call `validateAcknowledgementSet` from `@coachcal/core` against the request.
- `src/data/api/accountClient.ts`: `deleteAccount()` (`DELETE /v1/account`).
- `src/data/auth/sessionStore.ts`: the session (user and tokens) kept in `expo-secure-store`, loaded
  at start, cleared on sign-out, with the injected clock; exposes `getSession`, `onChange`,
  `getAccessToken` (refreshes when expired).
- `src/data/auth/authApi.ts`: one function per endpoint of `packages/api-contract/src/auth.ts`.
  Google: open `GET /v1/auth/google/start` with `expo-web-browser`, catch the redirect to
  `coachcal://auth/google?code=...`, then `POST /v1/auth/google/exchange`. Apple:
  `expo-apple-authentication` gives the identity token, the authorization code and the name on the
  first sign-in.
- `src/data/auth/appleNonce.ts`: a raw nonce from `apps/mobile/src/data/sync/uuid.ts`'s random
  source, hashed with SHA-256 through `expo-crypto` (`digestStringAsync`). Load `expo-crypto` lazily
  inside the function: the native build that the Simulator runs today predates that package, and a
  top-level import would crash the app there. If the hash cannot be computed, the Apple button is
  not shown and the error is typed. Read in `node_modules/expo-apple-authentication` (iOS source and
  typings) whether the button hashes the `nonce` prop itself: the owner found that it passes the
  nonce through, so the request must receive the hash and the server the raw nonce.
- `src/features/auth/SignInScreen.tsx`: props-driven (`onSignedIn(session)`), the three entry points
  with the identifiers above, built from `src/design` components (`PrimaryButton`, `SecondaryButton`,
  `SearchField` or a plain `TextInput` styled with the tokens for the email and code fields), busy
  and error states, the Apple button only when `AppleAuthentication.isAvailableAsync()` is true.
- Typed errors per boundary (`ScanApiError`, `SyncApiError`, `AuthError`, `AccountError`), plain
  objects, no `any`.
- `apps/mobile/.env.example`: `EXPO_PUBLIC_API_URL=http://127.0.0.1:8787` with a one-line comment.

## Method (test first)

One Swift test file at a time: write the Jest twin with one `it(...)` per Swift `@Test` and the same
sentence, see it fail, port the source until it passes. `fetch` is mocked with `jest.fn` and
answers with the golden files; `expo-secure-store`, `expo-apple-authentication`, `expo-web-browser`
and `expo-crypto` are mocked. Then the screen with React Native Testing Library (render is async:
`await render(...)`), one test per step of `SignInFlowTests` and per error state.

Tests live next to the code (never under `src/app/`). `npm run typecheck` regenerates the Expo Router
typed routes first, so `router.push('/onboarding')` in a test or in the screen is checked.
