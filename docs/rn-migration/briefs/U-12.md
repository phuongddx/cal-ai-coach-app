## Shape

- `src/data/db/schema.ts`: one Drizzle table per GRDB table, same column names, SQLite types,
  primary keys, foreign keys, indexes and constraints as in `Migrations.swift`.
- `scripts/rn/gen-migrations.mjs`: runs `npx drizzle-kit generate` in `apps/mobile` (drizzle-kit
  0.31.11 is installed at the root), then concatenates the SQL files under
  `src/data/db/migrations/*.sql` in file-name order into `src/data/db/migrations.ts`:
  `export const MIGRATIONS: readonly { id: string; sql: string }[]`, each entry one statement
  (split on Drizzle's `--> statement-breakpoint`). The generated file is never edited by hand.
  With `--check` it regenerates into a temporary directory and exits 1 when the committed files
  differ. Delete the hand-inlined `migrations.ts` content and start from a clean migration history:
  the first generated migration creates the 15 tables.
- `src/data/db/client.ts`: opens the `expo-sqlite` database, applies every entry of `MIGRATIONS` in a
  transaction on first launch (and the later ones in order), then exposes the Drizzle instance.
- Test engine: `sql.js` (installed at the root) through `drizzle-orm/sql-js`.
  `src/data/db/testing/sqlJsDb.ts` creates a database, applies `MIGRATIONS` and returns the Drizzle
  instance. Repositories take the `SQLiteDatabase` type from `drizzle-orm/sqlite-core`, which both
  drivers satisfy, so the same code runs on `expo-sqlite` in the app and on `sql.js` under Jest.
  The owner checked the recipe: applying the spike migration through `sql.js` and `drizzle-orm/sql-js`
  works in Node.
- Repositories in `src/data/repos/`, one file per Swift repository, same method names in camelCase:
  `diaryEntryRepository.ts` (`recordUpserts` writes the mirror rows, the details and one pending op
  per entry in ONE transaction, and writes tombstones), `outboxRepository.ts` (batch of at most 50
  FIFO, attempt counter, dead letter at 5 attempts), `syncMergeRepository.ts` (last writer wins
  through `compareCanonicalVersions`, skips rows that have a pending local op, keeps the cursor in
  `sync_state`), `catalogRepository.ts`, `targetRepository.ts`, `trackingRepository.ts` (water,
  exercise, weight, with the model clamps), `engagementRepository.ts` (streak state, badges,
  insights), `csvExport.ts` (the CSV as a pure function; writing the file is a later unit).
- Seed data: `src/data/db/seed/foods.json` holds the rows of `SeedDataManager.swift` unchanged
  (same values, same order); a test checks the row count and ten sampled rows against the Swift file.
- `src/data/sync/repository.ts` and `store.sqlite.ts`: keep them the storage of the sync engine, but
  on the Swift tables: a pull merge writes `diary_entries` and `diary_entry_details` through the
  sync merge repository, a local write enqueues `pending_ops`. The wire shapes stay in
  `packages/api-contract/src/sync.ts` and are not changed. Keep the `SyncStoreApi` interface and
  `inMemorySyncStore.ts` so `engine.test.ts` and `engineChange.test.ts` pass without edits.
- Ids come from `apps/mobile/src/data/sync/uuid.ts`; never `crypto.randomUUID` under `apps/mobile`.

## Method (test first, one Swift test file at a time)

1. Write the Jest twin with one `it(...)` per Swift `@Test` and the same behavior sentence.
2. Run it and see it fail.
3. Port the source until it passes.
4. Move to the next file.

Start with `MigrationTests` and `DomainMigrationTests` (they define the schema), then
`OutboxRepositoryTests`, `DiaryEntryRepositoryTests`, `DomainRepositoryTests`, `SeedDataManagerTests`,
`CSVExportServiceTests`, `AppLaunchMigrationTests`, `CoachCalPersistenceTests`.
