## Goal

Photographing, describing or scanning a meal runs the old scan flow on RN: capture, analyzing,
review with editable grams and recomputed kcal, save in one transaction with Undo, the saved card.
The model is a pure reducer with the Swift tests ported; the screens use the design system.

## Shape

- `features/scan/scanModel.ts`: the state machine as a pure module with injected dependencies, the
  way `ScanModel.swift` takes `api`, `persistence` and `now` in its `init`: the API client
  (`CoachCalApi`), `save`, `undo`, `notify`, `ownerId`, `now`, the capture seam, the activity port.
  Nothing under `features/scan` imports `src/data/environment`, `src/data/sync/runtime` or
  `src/debug`. States and transitions as in the Swift file: capture, analyzing, review, saving,
  saved, quota, failed.
- **The kcal rule (I6).** Every edit of grams recomputes the displayed kcal through
  `@coachcal/core` (`KcalArithmetic`) from the current grams. The response kcal is never the display
  source after an edit. One test edits grams and asserts the recomputed figure; the parity with the
  server rule is already a test in `packages/core`.
- **Save.** One call to the diary repository's `recordUpserts(upserts, now)`: mirror rows, details
  and one pending op per entry in one transaction; the model receives it as `save`. Then the
  injected `notify`. Undo calls `recordTombstone` and notifies again. Every entry carries the owner
  id the route passed: `getSessionStore().getSession()?.user.id`, or `DEMO_USER_ID` from
  `apps/mobile/src/data/repos/seedDataManager.ts` when no session exists (U-23 makes the store
  session-aware). A test with a fake repository asserts one `save` call for the whole save, as the
  Swift case `saveEnqueuesOnePendingOpPerEntryAndUndoTombstones` does.
- **Screens** in `features/scan/`, one file per Swift view, built from `src/design` components only.
  A component the design system lacks is built inside `features/scan` and named in the findings;
  the owner decides whether it moves to `src/design`.
- **ED-safe (I7).** Feature code holds no ED-safe branch: no `edSafe` call outside `src/design`
  (the components own it). The Live Activity content carries `edSafeMode` as the Swift attributes do;
  read the flag, do not branch on it in the feature.
- **Capture.** `expo-camera` for the photo and the barcode scanner, `expo-image-picker` for the
  library fallback, `expo-image-manipulator` to resize before upload. Read their docs and typings in
  `node_modules` before relying on an API (standing-order rule 13). The fixture image is
  `native/App/CoachCal/Resources/ScanMedia/fixture-meal.png`: copy it to
  `apps/mobile/src/features/scan/assets/fixture-meal.png` (copying out of the read-only `native/`
  is allowed) and load it with `require`. On the Simulator there is no
  camera: the capture seam shows the fixture image and reports access granted, as the Swift case
  `testFixtureCaptureSeamAlwaysReportsAccessGranted` says. The denied-permission card and its
  Settings escape are ported and tested; they cannot be shown on the Simulator.
- **Live Activity (PL-12).** `features/scan/scanActivity.ts` exports a small port with `start`,
  `update` and `end` and a no-op implementation. The model calls the port exactly where
  `ScanModel.swift` starts and ends the activity. The real implementation is U-43 (it needs a native
  build); do not try `expo-widgets` here.
- **Wiring lives in the route file.** `src/app/scan/index.tsx` is the only file of the feature that
  imports `getDataEnvironment`, `getSessionStore`, `getDebugFlags` and `notifyLocalMutation`
  (`apps/mobile/src/data/sync/runtime.ts`). It builds the model's dependencies and hands them to
  the factory in `features/scan/scanModel.ts`: the fixture API (`new FixtureScanApi(scenario)`) in
  fixture mode, otherwise `new LiveScanApi({ auth: getSessionStore().bearer, baseUrl:
  resolveBaseUrl() })` (`resolveBaseUrl` comes from `apps/mobile/src/data/api`); `save` bound to the
  diary repository's `recordUpserts` and `undo` to its `recordTombstone`; `notify` =
  `notifyLocalMutation`; the flags from `getDebugFlags()`; the owner id (see Save). Fixture mode is
  on when `scanScenario` or `fixtureCapture` is set. Launch arguments cannot be read on a device yet
  (U-51 needs a native module for it). Until then the scan route also accepts `scenario` and
  `capture` query parameters with the same meaning, honored only under `__DEV__`
  (`coachcal://scan?scenario=402`). U-51 replaces them.
- **Route.** `src/app/scan/index.tsx` default-exports the flow and nothing else: no tests under
  `src/app` (Expo Router makes every file a route).
