## Shape

A. **Random ids (security).** An independent review read the runtime sources: Hermes has no
   `globalThis.crypto` in RN 0.88, so `newUuid()` falls back to `Math.random` in a production build,
   and the Apple nonce is derived from two of those ids. `uuid.ts` takes its 16 bytes from
   `expo-crypto`'s `getRandomValues` through a lazy `require`, the way
   `apps/mobile/src/data/auth/appleNonce.ts` loads `expo-crypto`. No `Math.random` remains in the
   id source. Add `getRandomValues` to the Jest mock of `expo-crypto`
   (`apps/mobile/src/__mocks__/expo-crypto.ts` has only `digestStringAsync` today). Ids stay UUID v4
   (I11). Reword the comment in `uuid.ts` that names `crypto.randomUUID`; the parity gate looks for
   it.

B. **A push acknowledgement applies the record.** Today `store.sqlite.ts` `applyPushAcks` stamps only
   `serverVersion` and deletes the op. The server (U-21) does not number a losing operation: it
   answers `applied` with the record it keeps. So a device whose push lost keeps its own text under
   the winner's version, and the next pull skips the record as not newer. That is a permanent
   divergence. New rule: for each acknowledged operation, delete the op; when the record has no
   other pending local op, apply the returned record exactly like a pulled row (mirror row, details,
   version, accepted op; a deleted record becomes the tombstoned mirror row). When a newer local op
   is still pending for the record, leave the mirror alone. Tests: a losing upsert ack applies the
   server record; a losing tombstone ack restores the live record; an ack with a newer pending op
   leaves the mirror alone; a winning ack keeps the local content and stamps the version.

C. **One writer at a time on the handle.** `repos/sqlDb.ts` `inTransaction` runs raw
   `BEGIN`/`COMMIT`/`ROLLBACK`. Two overlapping calls break each other: the second `BEGIN` fails,
   its catch rolls back the first caller's open transaction, and the rest of the first body
   autocommits statement by statement. Serialize the calls on the database handle (a promise chain
   is enough) and roll back only a transaction the call owns. Test: two overlapping calls both
   complete whole; a throw inside one leaves nothing of that one and the other completes whole.

D. **The engine.** Port `SyncEngine.swift`, `Backoff.swift` and `SyncTriggers.swift` with one Jest
   case per Swift test, same behavior sentence: debounce of 500 ms after a local write, batches of
   50 FIFO, generation tokens, an op quarantined after 5 dispatch attempts (transport and server
   errors count), the acknowledgement set validated with `validateAcknowledgementSet` from
   `@coachcal/core`, 401 stops, pull pages until `hasMore` is false. The transport's `pull` rejects
   a cursor that moves backwards: call `validatePullResponse` from `packages/core` at the call site
   and map the contract rows (`{seq, record}`) to the shape it takes; `packages/core` is not yours.
   NetInfo and AppState have no manual mock: mock them per test file with `jest.mock`.
   The existing 14 engine tests keep passing or are replaced by twins, with one line per replaced
   test in the findings file.

E. **The session user.** `runtime.ts` builds the transport with the session store's token provider
   and refresh (`getSessionStore()` from `apps/mobile/src/data/auth`; read findings U-20 item 1).
   Mirror rows carry the user id of the session. The two constants that hard-code a demo owner
   (`LOCAL_OWNER_ID` in `store.sqlite.ts`, `DEMO_USER_ID` in `seedDataManager.ts`) apply only when
   no session exists (fixture and debug mode). Without a session the engine makes no request and
   reports `unauthorized`. Write in the findings what the Swift app does to the local store on
   sign-out and account deletion; the reset itself is U-51.

F. **End to end against the real API.** `scripts/rn/e2e-sync.sh` pins the spike's per-record
   counter. The ported SQL numbers every applied operation from one global sequence (the legacy
   behavior), so on a fresh cluster the first two operations get versions 1 and 2: fix the script,
   not the route. `scripts/rn/e2e-sync-app.sh` still reads the spike tables: point it at
   `diary_entries`, `pending_ops` and `sync_state` (you cannot run it: no Simulator; say so in the
   report). Add one integration suite that runs the real client engine and the SQLite store
   (`sql.js`) against the API on port 8787 and proves: two stores converge through edit, push,
   pull, edit, push, pull; a tombstone propagates; in an offline conflict the loser's store holds
   the server record after its acknowledgement. The suite skips loudly when the API slot is not
   held (same pattern as `[sql-skip]` in `apps/api/src/testing/sqlHarness.ts`).
