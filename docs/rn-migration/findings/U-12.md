# U-12 findings — mobile persistence

Worker: Worker-G1. Unit of `docs/rn-migration/plan.md`. Ports the local store of
`CoachCalPersistence` to `apps/mobile`: the Drizzle schema of the 15 GRDB tables, migrations
generated by `scripts/rn/gen-migrations.mjs` into a Metro-bundlable module, and the
repositories tested like the Swift tests on sql.js under Jest.

## 1. The transaction seam: not drizzle's `db.transaction`

The brief's recipe (drizzle-orm/sql-js over sql.js) works for queries, but drizzle 0.45.4's
sql-js session runs `BEGIN → callback → COMMIT` **without awaiting an async callback**
(`node_modules/drizzle-orm/sql-js/session.js`, `transaction()`): the commit fires before the
first `await` of the body resolves, so awaited statements run in autocommit mode and a
mid-body failure leaves rows behind — the atomic `recordUpserts` acceptance failed until the
repos switched to a raw `BEGIN … COMMIT / ROLLBACK` window
(`apps/mobile/src/data/repos/sqlDb.ts`, `inTransaction`). That helper behaves identically on
expo-sqlite (async) and sql.js (sync), which is what the dual-driver seam needs anyway. The
migration runner in `client.ts` and `testing/sqlJsDb.ts` uses the same raw pattern.

## 2. One generated migration, not three (per the brief)

Parity PL-03's target text says "every GRDB migration becomes one ordered SQL migration";
brief U-12 says "start from a clean migration history: the first generated migration creates
the 15 tables". The brief wins: `MIGRATIONS` is a single entry (`0000`) carrying all 15
tables, with `pending_ops.quarantined` inlined as the last column (the same final
`pragma table_info` order the Swift `2__outbox_dead_letter` ALTER produced). The registry
assertions of `MigrationTests`/`DomainMigrationTests` are adapted to that shape (ids,
`user_version`), documented in `parity-detail/data.md`.

## 3. Migration transport: `user_version` + generated `migrations.ts`

`gen-migrations.mjs` runs `drizzle-kit generate` (dialect sqlite, fresh out dir), then
bundles the SQL files in file-name order into `src/data/db/migrations.ts` as
`{ id, sql: readonly string[] }` — each entry one migration, each string one statement (split
on `--> statement-breakpoint`). Entry ids are the zero-padded file-order index, NOT drizzle
kit's random file names, so `--check` (regenerate into a temp dir, diff the bundle) is
deterministic. Applied by `client.ts` in per-migration transactions guarded by
`PRAGMA user_version`; the single-row `sync_state` seed (`INSERT OR IGNORE (1,0)`) runs after
migrating — drizzle-kit cannot express the GRDB seed insert. The old hand-inlined bundle
(`meals`/`outbox` spike tables) and the expo-driver `migrations.js` are deleted; a Jest twin
runs `--check` so editing `schema.ts` without regenerating fails `npm test`.

## 4. Dual-driver handle

drizzle 0.45.4 has no `SQLiteDatabase` alias in sqlite-core (the brief's assumption); the
equivalent seam is `BaseSQLiteDatabase<'sync' | 'async', any, typeof schema>`
(`apps/mobile/src/data/repos/sqlDb.ts`, `SqlDb`). Both `ExpoSQLiteDatabase` and
`SQLJsDatabase<typeof schema>` assign to it — verified by a throwaway tsc probe before
writing the repos. sql.js ships no types and adding @types/sql.js is a package change, so
`src/data/db/testing/sqlJs.d.ts` declares the minimal surface (`initSqlJs`, `Database`).

## 5. The sync store on the Swift tables (wire shapes unchanged)

`store.sqlite.ts` keeps the `SyncStore` interface (engine untouched, 14 tests pass
unchanged) but maps the meal-shaped wire records onto the Swift tables:

- local write = one transaction: `diary_entries` mirror + `diary_entry_details` row + one
  `pending_ops` row (`enqueueDiaryOp` writes the canonical snapshot JSON);
- delete = tombstoned mirror row + tombstone op (Swift keeps the mirror; the spike deleted it);
- push acks = `applyAcknowledgement` (canonical version bump when newer + op delete);
  content arrives with the next pull — Swift semantics, not the spike's overwrite-on-ack;
- pull pages = `applyPulledRow` (LWW via `compareCanonicalVersions`, pending-intent skip)
  plus the pulled detail rows in the same transaction, then the `sync_state` cursor.
- `pendingOperations` rebuilds the wire `SyncOperation` from the mirror + detail rows (the
  `pending_ops` snapshot column carries no nutrition); `markAttempts` bumps
  `dispatch_attempts` only — `pending_ops` has no error column and the engine owns backoff,
  so `next_retry_at` stays open (Swift's `markFailed` sets a caller-provided retry time; the
  outbox repo exposes exactly that API for its own tests).
- The store's owner is a module constant (`LOCAL_OWNER_ID` = the demo user id): the wire
  contract has no user field and auth is a later unit. Documented hand-off: when auth lands,
  thread the session user through `runtime.ts` (not this unit's file).
- `meal_slot` of a details row written by the sync store derives from `eatenAt` local hour
  (breakfast < 11, lunch < 15, dinner < 21, else snacks) — the wire `Meal` carries no slot.

## 6. Repos that needed no call-site changes

`binding.ts` and the three spikeActions/builtinActions files compile unchanged — the
`MealRepository`/`SyncStore` signatures are stable, so the "minimal call-site updates" the
brief allowed are zero. `binding.ts` is untouched.

## 7. `scripts/rn/e2e-sync.sh` and `e2e-sync-app.sh` (not edited, per brief)

Both query the spike tables. What must change when their owner updates them: `meals` →
`diary_entries` (`name` → `display_text`, `eaten_at` → `created_at`, `deleted` →
`deleted_at IS NOT NULL`), `outbox` → `pending_ops` (`payload` → `snapshot`,
`queue_seq`/`state`/`last_error` columns are gone — order is `created_at, op_id`, state is
`quarantined`), `sync_state` key/value rows → the single row (`pull_cursor` column), and the
fixture ids stay valid (text primary keys).

## 8. Shared API database drift found during the gates

`npm test` at the repo root failed in `apps/api` — not this unit's code: the shared local
Postgres (port 5433) had been built from a checkout newer than origin/main (it recorded a
`20260920000000_auth_accounts` migration that origin/main does not have, and its
`entitlements` table lacked the uuid user-mapping column that origin/main's
`20260914000000_scan_pipeline.sql` declares and the api tests query). Minimal fix applied:
the matching `ALTER TABLE public.entitlements ADD COLUMN IF NOT EXISTS` for that one column
(their `user_id` column and their running API process were left untouched). Whoever owns the
API stack should rebuild the throwaway cluster from one checkout (`scripts/rn/start-api.sh
stop` + `start`) so `schema_migrations` matches the source again.

## 9. Small adaptations, all test-proven

- `details(forDay:mealSlot:)` ports the Swift SQL join through drizzle's query builder (same
  `date(e.created_at, 'localtime') = ?` predicate, same ordering); sql.js evaluates
  `localtime` against the host zone like GRDB does.
- Tracking clamps (parity DB-06): `addExercise` clamps duration 0–600 and burned kcal 0–5000
  through `clamp` from @coachcal/core (rounded); the Swift model had no clamp — parity.tsv
  asked for it at the model boundary.
- Seed rows: `seed/foods.json` holds the 30 `SeededFood` rows verbatim (values + order); the
  meal/badge/insight fixtures stay in `seedDataManager.ts` with kcal/macros derived through
  the core arithmetic (`roundKcal`/`roundMacro`) — never a private copy.
- The CSV generator returns `Uint8Array` (the Swift `Data`); sections, header-from-first-row,
  blank-line separators and `csvField` escaping port line-for-line.
- `inMemorySyncStore.ts`, `fakeServer.ts`, `types.ts` and `repository.ts` needed no changes;
  they stay as the engine's test seams.
