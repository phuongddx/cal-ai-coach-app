# U-82 — the React Native gates on GitHub Actions (the iOS half)

Worker: Worker-G1, 2026-11-28. The integration half (rn-ci.yml, scripts/rn/ci) went to main with
PR 65; this document is about the iOS half that PR 58 still carries, rewritten after the
correction round of the re-read review (docs/rn-migration/reviews/U-82-PR-58-reread.md).

## What the workflows do

- `rn-ios.yml` (new): `macos-26`, 90-minute timeout, concurrency per pull request (a newer push
  cancels the older run): `npm ci`, `npx expo prebuild --platform ios` (generates `ios/` and runs
  pod install), `xcodebuild` of `ios/CoachCal.xcworkspace` scheme `CoachCal` Debug for
  `iphonesimulator` with `CODE_SIGNING_ALLOWED=NO`, boot of an available iPhone on the newest
  iOS runtime (`scripts/rn/ci/pick-simulator.sh` — the run log shows "iPhone Air - iOS 26.5"),
  install, Metro via `npx expo start --dev-client` with `scripts/rn/ci/wait-metro.sh` waiting on
  `packager-status:running`, Maestro from `get.maestro.mobile.dev` (JAVA_HOME to the runner's
  JDK 21 when present; `MAESTRO_DRIVER_STARTUP_TIMEOUT: 300000` for the cold simulator), and ONE
  STEP PER FLOW so a run gives an answer per flow, with artifacts (screenshots, reports, the
  Metro log) on `always()`.
- `.maestro/` — five flows. Launch arguments (`--ccSeedNoTargets`, `--ccScanScenario 200`,
  `--ccEDSafe`) come from the workflow's `simctl launch`, never from Maestro (see pitfall 1);
  each flow only `openLink`s the dev-client URL. Order: 01 a fresh install shows onboarding;
  02 seeds the demo persona (`--ccSeedNoTargets` launch → `coachcal:///?seed=1` → the seeded
  Today); 03 the four tabs and the diary sheet on the seeded persona; 04 the scan fixture
  recomputes kcal (464 → three taps → 508); 05 `--ccEDSafe` hides the kcal clause of the seeded
  meal row.
- The rn-ci.yml half is on main (PR 65): the `integration` job with the `postgres:17` service,
  the `[sql-skip]` guard, the smokes and the sync script; the `test` job runs Jest with
  `--testTimeout=120000` (the 15 s default of apps/mobile, apps/mobile/jest.config.js, fired
  locally on a loaded machine on `todayScreenSnapshotMatrix`; proven green at 120 s).
- `ci.yml` untouched: it already carries the `native/**` + own-file path filters on main.

## Findings and pitfalls

1. **Maestro `launchApp` arguments are a key-value map**, not a list, and on iOS they land as
   `-key value` pairs — the `--cc*` parser of `apps/mobile/src/debug/launchArgs.ts` (bare flags,
   value in the NEXT argument, double dash) never sees them. The flows that need launch
   arguments are launched by the workflow with `xcrun simctl launch <udid>
   com.nextlabs.coachcal --ccScanScenario 200` / `--ccEDSafe` / `--ccSeedNoTargets` — the way
   scripts/rn/evidence/lib.sh `app_open` does it — and the flow itself only `openLink`s the
   dev-client URL (`exp+coachcal://expo-development-client/...`), which keeps the process
   arguments intact. (Source: docs.maestro.dev `launchApp` reference.)
2. **`${{ runner.temp }}` is not allowed in job-level `env:`** (only `github`, `inputs`,
   `matrix`, `needs`, `secrets`, `strategy`, `vars` contexts). The first push failed in 0 s with
   "workflow file issue"; `actionlint` names the exact context rule. The env file variable moved
   to step-level `env:`, where the `runner` context is allowed.
3. **The smoke scripts take `PG_BIN` as a directory** (`"$PG_BIN/psql"`); the runner's client is
   at `/usr/bin`, so the rn-ci.yml integration job sets `PG_BIN: /usr/bin` (the scripts'
   homebrew default is macOS-only). `jq`, `curl` and `openssl` are preinstalled on
   `ubuntu-24.04`; the job guards `psql` and `uuidgen` with `command -v … ||` installs.
4. **The seeding mechanism**: `coachcal://debug?action=seed` (the spike action,
   sync/spikeActions.ts) adds only the two fixture meals and NO target, so on a fresh install
   the root gate stays on onboarding — proven by run 46132732255, whose failure screenshot shows
   the onboarding hero. The full demo persona (one target, `seedDataManager.ensureSeeded`) comes
   from `coachcal:///?seed=1`, which only mounts when the shell can (hence the
   `--ccSeedNoTargets` launch of flow 02) and only under `__DEV__` (app/(tabs)/index.tsx:77-80);
   a debug build served by Metro is `__DEV__`.
5. **The system "Open in CoachCal?" dialog**: every `simctl openurl` of a custom scheme raises
   it and Maestro's `openLink` does not confirm it — run 46128027791 sat on the dialog for the
   whole first wait (its artifact screenshot shows the launcher home with the dialog up). Fixed
   with an optional anchored tap (`^Open$`) after every openLink; the anchor is needed because
   map-form `text` is regex and an unanchored "Open" would also match "Open diary".
6. **`${{ runner.temp }}`**: see pitfall 2. **`--no-open`**: `expo prebuild` of @expo/cli 58 has
   no such flag (run 46116842300 failed in 1 s); CI has no TTY to open anything.
7. **Maestro driver startup**: the XCTest driver compiles on the cold CI simulator;
   `MAESTRO_DRIVER_STARTUP_TIMEOUT: 300000` (job env) — run 46122777804 died with "iOS driver
   not ready in time" before the variable existed.
8. **Text matching**: Maestro shorthand selectors match the whole text; map-form `text` is
   regex. The section headers carry a slot emoji, the uppercasing of SectionHeader is
   style-only (the accessibility tree carries the raw string), and the meal row title is the
   raw meal title — hence `.*Breakfast` as a regex and the exact strings everywhere else.
9. The correction round itself: five must-fixes of the re-read review landed (the Coach and
   Profile markers, the seeded meal's name, the capture screen's wait, the GramsField id), plus
   should-fix 6 (flow 05 asserts the kcal clause of the SAME row flow 03 shows, so the
   assertion cannot pass empty) and note 8 (one flow per step).

## Not verified here

- The iPhone Air screen of the runner (iOS 26.5) is the only device the flows have run on; a
  different runner image may pick a different device (the picker takes the newest runtime's
  first iPhone, no pinned name).
- Maestro's exact tolerance for a late system dialog behind `optional: true` is the CLI's
  default wait; the runs so far always raised the dialog within it.
