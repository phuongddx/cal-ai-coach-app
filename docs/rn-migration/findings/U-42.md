## 1. The service over a port, not over the library

`HealthKitService.swift` abstracts `HKHealthStore` behind the `HealthStoring` protocol; the RN
counterpart is `HealthKitNativePort` in `data/health/healthKitService.ts` — six calls
(`authorizationStatusFor`, `requestAuthorization`, `enableBackgroundDelivery`,
`queryQuantitySamplesWithAnchor`, `saveQuantitySample`, `queryCorrelationSamples` +
`deleteObjects`), identifiers as plain HK strings and the ObjC enum values mirrored as local
consts (`AuthorizationStatus` 0/1/2, `ComparisonPredicateOperator.equalTo` = 4,
`UpdateFrequency.hourly` = 2). The service module imports the library as types only, so no Jest
run ever loads its Nitro hybrid objects — the spike's own mock header marks that as fatal. The
real port (`data/health/healthKitNative.ts`) is the only runtime import of the library; it owns
every cast to the library's branded identifier unions. It is imported today only by
`features/onboarding/healthAccess.ts` (route-level, per the U-31 convention); the Today/diary
units will reuse the same factory.

Two library facts worth recording (both checked in `node_modules`, rule 13):

- expo-notifications 58 has no `removePendingNotificationRequestsAsync` — the pending-request
  concept lives on `UNUserNotificationCenter`, and the expo counterpart is cancelling scheduled
  notifications by identifier. `refreshNotifications()` cancels exactly the three CoachCal
  identifiers before re-adding, which is the Swift remove-and-replace (T-P44-02).
- expo-file-system 58's `cacheDirectory`/`writeAsStringAsync` moved to the `/legacy` subpath;
  the repo pattern (`spike/firstRender.ts`) uses the new `File`/`Paths.cache` API and this unit
  follows it.

## 2. The CSV binding: `prepareCsvExport`, not `exportCsvAndShare` (deviation, needs the owner's call)

The brief binds `csvExportAction` to `exportCsvAndShare()`. Binding it verbatim would present the
share sheet every time Settings opens: the settings model pre-computes the export on mount
(`loadExport()` in the route's `useEffect`, the RN shape of Swift's `.task` guard), and
`exportCsvAndShare` hands the URL to `expo-sharing` as its last step. The Swift behavior shares
on tap (`ShareLink`), not on load.

Resolution inside the writable scope: the route binds `prepareCsvExport()` — it builds the
generator's output, writes the same cache file, and returns the text, so the model, the view and
the tap-time share behave exactly as before (parity preserved). `exportCsvAndShare()` exists,
shares through `expo-sharing` with `mimeType: 'text/csv'`, and is fully tested
("exportCsvAndShare writes the generator output to the file and the share port receives its
URL"). Its caller is recorded in parity-detail/health.md as pending: making the export row share
the file URL is a one-line change in `features/profile/SettingsDetailView.tsx` (out of this
unit's scope). If the owner prefers the literal binding, it is a one-line swap here.

## 3. The OB-03 narrowing, end to end

`healthAccess.ts` now asks through the service: `requestAuthorizationIfNeeded()` checks the step
type's status, requests `{ toShare: [], toRead: ['HKQuantityTypeIdentifierStepCount'] }` only
while `.notDetermined`, and re-checks after the sheet. The five-type ask U-31 shipped is gone;
the `'granted' | 'denied'` contract (errors map to `'denied'`) is unchanged, so the screen, the
model and all nine screen tests pass untouched. The narrowing is proven twice: at the service
level (doubles) and through the real library mock (`healthAccess.test.ts` reads the recorded
`authRequest`).

## 5. Small port decisions

- `burnAddBackEnabled` is async on RN (the flag lives in `app_settings`, not `UserDefaults`) and
  answers false until a caller injects `readBurnAddBack` — the `NoOpHealthKitService` default.
  The key is not re-spelled: the default reader is the caller's job, and the key constant stays
  `platform/storedFlags.ts` (`BURN_ADD_BACK_SETTING_KEY`).
- The anchored step query keeps the Swift anchor across calls (`anchor` field), queries
  midnight-to-now with `strictStartDate` (Swift's `.strictStartDate` predicate), and aggregates
  with the pure `aggregateStepCount`.
- `refreshNotifications()` swallows per-call center failures like Swift's `try?`, including the
  cancellation call (Swift's removal is synchronous; the RN promise can reject).
- The notification port's default (`expoNotificationCenter`) is exported separately so the
  calendar-trigger mapping is testable over the library's manual mock (which has no
  cancel-pending API — the mapping test exercises scheduling only; the idempotent replace is
  proven on the injected port).
- The expo-notifications mock in `src/__mocks__/` needed no change; every new suite drives its
  own doubles. `expo-file-system` is mocked with an inline factory in the CSV suite (no new
  mock file, no new package).
