# U-32 findings — diary

Worker: Worker-G2. Unit of `docs/rn-migration/plan.md`, wave 3. Ports the diary day sheet and its
six sheets (DY-01 to DY-07): `apps/mobile/src/features/diary/` (models, screens, tests), the route
`apps/mobile/src/app/diary.tsx`, `docs/rn-migration/parity-detail/diary.md`.

## 1. The water rule lives in the diary feature, not Today

The Swift twin drives `TodayModel.logWaterDelta` (the clamp is Today's code). Today is U-33's, so
the same rule ports into `waterModel.ts` (DY-07 owns the water card): `logWaterDelta` computes
`max(current + delta, 0) - current`, writes nothing when the applied delta is 0, and lands the
applied delta as one `water_logs` row. The model also carries `waterMl`/`glasses` with the
`waterGlasses ?? 8` default, so U-33 can mount `WaterCard`/`WaterLogSheet` without re-porting
anything. After the local-only write it calls `notify` anyway (brief: Today re-reads), and refreshes.

## 2. Concurrent re-log batches run through a feature-local write queue

The Swift test calls `performRelog` twice concurrently and relies on GRDB serializing at the pool.
The RN `inTransaction` seam does not serialize overlapping callers (U-12 finding; the serialized
transactions are U-23's), so two raw concurrent `recordUpserts` interleave and break. This unit
therefore serializes its own multi-statement writes (`writeQueue.ts`): `AddFoodModel.relog` and the
manual-log saver queue behind one another. The twin's "concurrent relog batches leave no partial
state" drives the MODEL (both batches land: details 3, kcal sorted [86, 380, 464], 3 ops) — the same
behavior sentence, proven at the seam the app actually uses. The Swift view-level single-flight
(`isRelogging`) stays a view concern (`AddFoodSheetRoute` drops taps while a re-log runs in the RN
container too). When U-23 lands serialized transactions, the queue becomes redundant but harmless.

## 3. Reconciliation for the Swift `meals.count == 3` literal

`testDiaryDayBoundaryGroupsByLocalCalendarDay` ends with `waitForToday(model) { $0.snapshot.meals.count == 3 }`.
The seed puts exactly one meal on today (Spaghetti Bolognese, dinner — the suite's own snapshot
comment says so), and the test inserts three lunch rows on today (noon, 19:00, 23:30 local) plus one
breakfast row the next day. Today's meal count is therefore 4, and `TodayDiarySnapshotTests`
confirms the seeded day carries the dinner meal. The RN twin keeps the test's real assertions (the
three boundary lunches group under today's lunch in order; nothing leaks into breakfast; the
boundary-nextday row lands on the next local day) and asserts today's items explicitly (3 boundary
+ the seeded dinner). If the Swift literal was meant to exclude the seed, that adjustment belongs to
the owner; the RN behavior (local-calendar-day grouping at every edge) is identical.

## 4. Model shape: the pool goes through the constructor, the query stays real

`DiaryDayModel` takes the open database handle plus the repositories through its deps (Swift takes
the pool), and builds its snapshot loader over them. The loader lives in `diarySnapshot.ts` so the
model file stays free of drizzle imports while the twin exercises the REAL join (the localtime day
grouping of the SQL is part of CR-02). `deleteEntry` reads the mirror row through the data layer's
`fetchDiaryEntry`; `delete` tombstones then deletes the detail row in the Swift order (the details
join filters tombstoned rows, so no ghost renders even between the two writes).

## 5. Route file: the only data-seam consumer

`src/app/diary.tsx` builds the deps bundle (repos from `getDataEnvironment()`,
`notify: notifyLocalMutation`, owner id from `getSessionStore().getSession()?.user.id` with the
`DEMO_USER_ID` fallback, `now` from the environment clock, `newUuid`) and constructs the day model.
`getDebugFlags()` is NOT imported: the old diary feature reads no launch args. The runtime's
`subscribe` needs a wrapper that queues listeners until `getSyncRuntime()` resolves (the model
subscribes synchronously in its factory). The scan hand-over (`onCapture`) dismisses the diary
sheet and pushes `/scan?mode=…` — the scan route's parameter contract belongs to U-30; the push
shape may need a one-line adjustment when that lands. The water card/log sheet are components of
this feature but are NOT mounted by the diary route (the old DiaryDayView has no water card —
TodayView mounts them, U-33).

## 6. RNTL 14 (jest-expo/ios) — what the screen tests needed

- `render` is async and must be awaited; `screen` throws "\`render\` function has not been called"
  until the awaited render binds it. Sync assertions right after a `fireEvent` state change see the
  stale tree — the established repo pattern (`SignInScreen.test.tsx`, `EmberView.test.tsx`) is
  `await userEvent.press(...)` and `waitFor`/`findBy*` after any state-changing interaction; the
  screen tests follow it.
- `userEvent.press` needs the pressable element itself (a wrapper View with the testID silently
  does nothing); `fireEvent.press` bubbles up only. Where the Swift identifier sits on a DS
  component (no testID prop — the DS is frozen), the feature wraps it in a View with the same
  string and tests press `within(getByTestId(...)).getByRole('button')`.
- The design-system buttons carry no testID, so `manual.save`, `custom.save`, `exercise.save` are
  wrapper Views around `PrimaryButton`. The DS `Stepper`'s buttons keep the DS identifiers
  `ccstepper.decrement` / `ccstepper.increment`, which the Swift serving/duration steppers reuse.
- Elements hidden from accessibility (the water ring, as in Swift) need
  `getByTestId(id, { includeHiddenElements: true })`.
- Role+name queries (`getByRole('button', { name: … })`) do not match inside an RN `Modal`; modal
  content is otherwise fully queryable (`findByText`, `findByTestId`, `within(...).getByRole(...)`
  without a name all work). The screen tests avoid name-matched role queries inside modals.
- The dual-react preamble of `SignInScreen.test.tsx` is not required for these suites (with or
  without it, behavior is identical); the tests follow `EmberView.test.tsx` and omit it.
