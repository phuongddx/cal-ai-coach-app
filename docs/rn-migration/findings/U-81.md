# U-81 findings — the root gate on a fresh install

Worker: Worker-S2. Parity rows PL-01 and PL-05. A fresh install now shows onboarding. The cause was in
`app/_layout.tsx`: the guarded stack groups had no `redirectTo`, so expo-router chose the fallback screen itself, and
it chose the Debug console.

## 1. Reproduction (before the fix)

Fresh install (`app_install_fresh`), then `app_open` with no workaround, on iPhone 17 Pro, iOS 26.4, the dev client of U-79.

- What the gate decided: `onboarding` (probe line `render gate=onboarding`, see section 2).
- What the navigator showed: `pathname=/debug segments=["debug"] innerRoutes=["debug"]`. The screen is the Debug console.
- Screenshot: `docs/rn-migration/evidence/PL-01/fresh-install-before.png` (the Flags card and the Tabs/glass/Ember card).

## 2. The cause, proven by a log

**One sentence:** the navigator state is born from the launch URL `/` (the `(tabs)` route) while the gate still shows the
spinner; when the gate then decides `onboarding`, `(tabs)` is guarded, and with no `redirectTo` expo-router falls back to the
first unguarded file route in alphabetical order, which is `debug` (always mounted, never guarded), not `onboarding`.

Log (a temporary `console.log` in `RootLayout`, one line per render; removed before the commit). The full copy is
`docs/rn-migration/evidence/transcripts/U-81-gate-probe.txt`.

```text
BEFORE the fix
+1198ms render gate=wait        pathname=/       segments=["(tabs)"]  innerRoutes=["(tabs)"]
+1578ms render gate=onboarding  pathname=/       segments=["(tabs)"]  innerRoutes=["(tabs)"]
+1654ms render gate=onboarding  pathname=/       segments=["(tabs)"]  innerRoutes=["(tabs)"]
+1668ms render gate=onboarding  pathname=/debug  segments=["debug"]   innerRoutes=["debug"]

AFTER the fix
+133ms  render gate=wait        pathname=/            segments=["(tabs)"]      innerRoutes=["(tabs)"]
+262ms  render gate=onboarding  pathname=/            segments=["(tabs)"]      innerRoutes=["(tabs)"]
+348ms  render gate=onboarding  pathname=/onboarding  segments=["onboarding"]  innerRoutes=["onboarding/index"]
```

Reading it in time order: the navigator holds `(tabs)` from the first render (`gate=wait`, the URL `/`); the gate decides
`onboarding` at +1578 ms and the navigator is still on `(tabs)`; the guard then moves it, and it moves to `/debug`.

Source in `node_modules/expo-router/build`:

- `layouts/GuardContext.js` `findDefaultRedirectRouteInNavigator`: the fallback is the anchor
  (`unstable_settings.anchor = '(tabs)'`) if it is unguarded; otherwise the first child of the navigator that is not a redirect
  and not guarded, in `sortRoutesWithInitial` order (file-route order, alphabetical). `resolveGuardRedirects` uses that
  fallback only when `redirectTo` is `undefined`; with a `redirectTo` it uses `{ type: 'redirect', href }`.
- In the fresh-install state `(tabs)` is guarded (route is `onboarding`), and `debug` sorts before `onboarding` and `sign-in`.
- `useScreens.js` `GuardedRouteRedirect` renders the `Redirect` to the `redirectTo` href, or the replace to the fallback.

The Jest tests of U-51 decide the route in `rootController` and never mount the router, so they could not see it.

## 3. The fix (`apps/mobile/src/app/_layout.tsx`, 14 lines added, 3 changed)

A constant `GATE_HOME = { wait: '/', 'sign-in': '/sign-in', onboarding: '/onboarding', shell: '/' }` and
`redirectTo={GATE_HOME[route]}` on the three `Stack.Protected` groups. A guarded screen is now sent to the gate's own route.

- It holds for the three routes: fresh install to onboarding, signed-out user with a target to sign-in, user with a target to the
  shell (`/` is `(tabs)`). The device run and the unit test below cover each.
- No second gate: the decision stays in `decideRootGate`; the layout only names the destination of the guards it already had.
- No delay: no timer, no extra render state. The log shows onboarding 86 ms after `gate=onboarding` is first rendered.
- The Debug screen stays unguarded and reachable.

After the fix: `docs/rn-migration/evidence/PL-01/fresh-install-after.png` (onboarding, "Track calories with a photo", Get started),
regenerated by flow 01 on every run.

## 4. The test that would have caught it

`apps/mobile/src/__tests__/rootLayoutGate.test.tsx` (7 tests). It renders the real `RootLayout` (and its `unstable_settings`) in
expo-router's own `renderRouter` over a stub route table, with a controller double that decides the gate route, and asserts the
pathname and the screen the navigator reaches after a launch from `/`. Note on the brief: it uses the real router, not a double
of `expo-router`, because a double of the router cannot reproduce a defect of the router's own guard fallback.

Cases: fresh install shows onboarding; signed-out user with a target shows sign-in; user with a target shows the shell; the
spinner shows until the gate decides; a gate change moves the navigator (onboarding saved a target, then the shell); a sign-in
requirement while onboarding is open moves the navigator to sign-in; the Debug console stays reachable in every gate state.

- **Without the fix** (`redirectTo` removed): `Tests: 4 failed, 3 passed, 7 total`. The failures read `Expected: "/onboarding"
  Received: "/debug"`, the same for `/sign-in`, and the same for `/` after the gate change.
  Transcript: `docs/rn-migration/evidence/transcripts/U-81-layout-test-without-fix.txt`.
- **With the fix:** `Tests: 7 passed, 7 total`.
  Transcript: `docs/rn-migration/evidence/transcripts/U-81-layout-test-with-fix.txt`.
