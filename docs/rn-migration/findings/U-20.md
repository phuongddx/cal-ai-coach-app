# U-20 Mobile networking and auth client: findings

Date 2026-11-27. Branch `rn/u-20-networking-auth`. JS only: no native build, no Simulator.

## Result

The mobile app talks to the Hono API through typed clients over `@coachcal/api-contract`, with no reference to
the old backend client under `apps/mobile/src`. Rows NW-01 to NW-04 and AU-01 have code, Jest twins and a detail
file (`parity-detail/networking-auth.md`).

## What was added

- `src/data/api/`: `http.ts` (`apiRequest`: base URL, bearer, contract parsing, error envelope, one refresh and one
  retry on 401), `scanClient.ts` (`CoachCalApi`, `LiveScanApi`, `ScanApiError`), `syncClient.ts` (reworked: injected
  token provider and refresh, same call sites), `accountClient.ts`, `index.ts`.
- `src/data/auth/`: `sessionStore.ts` (secure storage, restore, single-flight refresh), `authApi.ts` (one function per
  endpoint of `packages/api-contract/src/auth.ts`), `appleNonce.ts` and `appleSignIn.ts`, `authServices.ts`,
  `index.ts` (memoized wiring), `types.ts`.
- `src/features/auth/SignInScreen.tsx` and `src/app/sign-in.tsx`.
- `src/testing/`: `fixtureScanApi.ts`, `mockFetch.ts`, `syncGolden.ts`, `fixtures/`.
- `src/__mocks__/expo-crypto.ts` (real SHA-256 through Node), an expo-crypto smoke test, `.env.example`.

## Decisions

1. **Clear the session only on a definitive rejection.** A refresh the server answers with a 4xx other than 408 and 429
   clears the session; a dropped connection or a 5xx keeps it and the stale token is returned, so a flight-mode
   launch does not sign the person out.
2. **Refresh is single-flight.** The refresh token rotates, so two concurrent refreshes would revoke each other.
3. **The Apple nonce.** `expo-apple-authentication` passes `nonce` through unhashed (read in
   `node_modules/expo-apple-authentication`): the request to Apple gets the SHA-256 hex, the server gets the raw nonce.
   `expo-crypto` is required inside the function (Jest has no dynamic `import()`), so a build that predates the
   package yields `AuthError nonceUnavailable` and no Apple button instead of a crash at import.
4. **No token, no request.** The sync transport with a null token is `SyncError('unauthorized')` and sends nothing.
5. **`SyncApiError` is an alias of the existing `SyncError`**, so the sync engine's error handling is unchanged.
6. **Sync goldens.** The Swift sync goldens are the old `diary_entries` row shape and do not decode under the Meal-record
   sync contract, so `src/testing/fixtures/sync_*.golden.json` were authored in the new shape (and are decoded by
   `goldenFixtures.test.ts`). The owner may move them to `packages/api-contract/golden/`.

## Findings for later units

1. **Wiring is left to the owner of `src/data/sync` and `binding.ts`** (not writable here): `runtime.ts` still calls
   `createFetchSyncTransport()` with no arguments, i.e. the dev token. To use real sessions:
   `createFetchSyncTransport({ tokenProvider: getSessionStore().getAccessToken, refreshSession: getSessionStore().refresh })`.
   `getSessionStore().bearer` is the bearer source for the scan and account clients. `getSessionStore().load()` must run
   once at launch; the route guard (signed-out users to `/sign-in`) is also not part of this unit.
2. **`jest.setup.ts` resets the manual mocks through `jest.requireMock(name).__reset`**, which is not the instance that
   `require`/`import` resolve to for `expo-apple-authentication`, so call counts leak between tests. `appleSignIn.test.ts`
   clears them itself. `jest.setup.ts` is outside this unit.
3. **`newUuid` falls back to `Math.random`** when no secure source exists. The Apple nonce is built from two `newUuid`
   values (64 hex characters), so on such a device the nonce is weaker than `SecRandomCopyBytes`. Whether the Expo runtime always provides a secure source was not checked; the owner of `src/data/sync/uuid.ts` may drop the fallback.
4. **The Google redirect.** `coachcal://auth/google?code=` is intercepted by the auth session of `expo-web-browser`;
   if the system also hands it to expo-router, `/auth/google` matches no route. The route table has no such file, on
   purpose: `app/` is not writable here. Check on a device (needs the U-21 server).
5. **Design buttons have no `testID`.** The screen wraps them in views carrying the `auth.*` ids; tests press by label.
   A `testID` prop on `PrimaryButton` and `SecondaryButton` would let UI tests target the button itself.
6. **The pull cursor check of the core `PullResponse.validate`** was not applied: it belongs to the legacy row shape.
7. **Account deletion** only calls the API; wiping local data and signing out afterwards belongs to the account-reset flow.
8. **Root `npm test` and the shared SQL database.** The SQL-backed suites of `apps/api` failed in this run with
   a Postgres error "column ... does not exist" on the old user-id column of the owner table (7 suites, 18 tests), against the local database the harness found.
   `apps/api` is unchanged by this branch; the schema of that database is out of step with the migrations on this base.
