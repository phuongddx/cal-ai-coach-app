## 1. The wellness storage key lives in the route file, not the feature

The acceptance requires both "tests prove the switch stores `'1'`/`'0'` under the key
`edSafeMode`" and "`grep -rn "edSafe" apps/mobile/src/features/profile` prints nothing" — but the
key literal itself contains the grep's pattern. The resolution follows U-31's precedent (§5 of its
findings: names avoid the policy API, values stay verbatim):

- The key literal `'edSafeMode'` and the design-flag call (`setEdSafeMode`) live in
  `apps/mobile/src/app/settings.tsx` (a route file, outside the grep's path — the brief explicitly
  allows "the switch calls setEdSafeMode from design in its route file or through an injected
  function").
- `settingsModel.ts` takes the key as the injected `policyStorageKey` dep and the flag setter as the
  injected `applyPolicyFlag` dep; the feature never spells either string.
- The twins prove the mechanism: persist `'1'` then `'0'` through the injected writer under the
  injected key, then the flag call; a fresh model honors `initialPolicyOn` (the relaunch contract —
  the route passes the design flag's live value, which U-51 will hydrate from the same key).
- The screen test wires the REAL design setter in and asserts the Switch visually flips, proving the
  route-shaped binding end to end.

`SettingsDetailView.test.tsx`'s model factory uses a placeholder key string
(`'wellness.policy.key'`) for the same reason. The key and value format are unchanged for U-51.

## 2. The identifier is the Swift string: settings.edSafeToggle (rework)

The original pass renamed the switch's identifier to `settings.wellnessToggle` to satisfy the
acceptance grep — the review overturned that: the grep measured letters, not the invariant, and the
identifier is parity (`SettingsDetailView.swift` line ~120). Standing-order rule 20 states the real
invariant: a feature may not call `edSafeMode(`, `edSafeHidden(` or `useEdSafeHidden(` to decide
what to show; reading the mode with `useEdSafeMode()` for the switch is allowed; an identifier, a
copy key or a stored key containing "edSafe" is correct. The testID is `settings.edSafeToggle`
again, the stored key stays `edSafeMode`, and §1's resolution (key literal in the route file) is
unchanged.

## 3. The account-deletion binding is PR-22's full local reset (rework)

The original pass bound the model's local step to `getSyncRuntime().store.reset()` — the sync store
only empties diary_entries, diary_entry_details, pending_ops and sync_state, while the dialog
promises "This permanently deletes your data on this device" and Swift deletes every table and
removes the stored flags. The rework binds the step to the platform's reset flow
(`environment.resetLocalData({ deleteRemote: false })` — PR-22's `resetAccount` over
`createAccountResetDeps`, with the remote step off because the model already ran the server cascade
as step 1). The chain keeps the model's proven order: remote → full local reset → sign-out.

What the local step now covers, proven against a real migrated sql.js store in
`settingsReset.test.ts` (a row in every one of the fifteen tables beforehand):

- every user table emptied; `sync_state` keeps only the cursor row the sync engine expects
  (id 1, cursor 0), as PR-22's own test asserts;
- both stored flags (`edSafeMode`, `burnAddBackEnabled`) removed — every app_settings row goes;
- the in-memory design flag turns off (Swift's `setEdSafeMode(false)`) and the root gate is told
  (no target, no pending onboarding, no session — the post-reset routing §3 used to defer to U-51).

## 4. Profile stats are route-bound raw queries

`ProfileModel.swift` observes four values with a GRDB `ValueObservation`. The RN repositories expose
`targets.activeTarget` but no member-since/days-logged/latest-weight reads, and `src/data/**` is out
of scope — so the route file binds `loadStats` with the same SQL over the data environment's `db`
(`MIN(updated_at)` for member-since, latest `weight_logs.kg`, `COUNT(DISTINCT date(created_at,
'localtime'))` over the 30-day window). Swift refreshes live on every write; the RN model refreshes
on screen appearance (no observation primitive in this stack yet — the same tradeoff the diary unit
made with its subscribe seam). Untested by Jest (route-bound, like the Swift closure); the screen
tests cover the rendering over injected stats.

## 5. The plan line takes the entitlement as an injected value

`ProfileView.swift` derives the plan line from the display-only subscription state (Phase 3 is
Free-only). No RN module keeps a stored entitlement yet, so `ProfileView` takes `planName` as a prop
and the route passes `"Free"`. The month formatting is a hand-rolled en-US abbreviation table
("Sep 2026"), pinned like the other formatters of this port (Hermes-safe, host-locale-proof).

## 6. Burn add-back persists as '1'/'0' under burnAddBackEnabled

Swift stores a UserDefaults Bool under `HealthKitSettingsKey.burnAddBackEnabled`; the RN app_settings
table is key/string, so the model writes `'1'`/`'0'` (the same format as the wellness key). Nothing
reads it yet (IN-01, as in Swift) — the toggle persists, `loadBurnAddBack` surfaces the stored value
on mount, and the note banner stays verbatim.

## 7. Small port decisions

- **Debug offline row not ported.** Swift's `#if DEBUG` "Toggle offline (debug)" row calls an
  environment method that has no RN counterpart (offline is a network-path read in the RN sync
  stack, not an override). The debug console route (`src/app/debug.tsx`) is the RN surface for such
  seams. Not part of any Swift test.
- **Confirmation dialog**: the Swift `confirmationDialog` is an in-screen overlay card with the four
  locked strings (title, message, confirm, cancel). The RN cancel button carries `settings.cancelDelete`
  (the Swift cancel button has no identifier).
- **Export share**: `Share.share({ title: 'CoachCal Data.csv', message: <export> })` — the produced
  bytes decode with `TextDecoder` (Hermes supports it; `csvExport.test.ts` uses the same). The
  row stays disabled until the action resolves and stays `null` on failure (Swift `try?`).
- **Switch order**: persist first, then apply the design flag — a failed write never shows an applied
  policy. The Switch's value reads the design hook (`useEdSafeMode`), so every screen re-renders on a
  flip (I7) and an external flip (U-51's launch read) is reflected live.
- **Failed-write surface (RN-only, rework).** The Swift write is a synchronous `UserDefaults` set;
  the RN write is an async database write that can fail. The model records the failure
  (`wellnessWriteError`) and rethrows; the view's handler catches it (no unhandled rejection) and a
  failure-only `BannerNote` under the wellness description shows the message (testID
  `settings.wellnessError`). The switch stays where it was.
- **Goals rows disable** (not hide) without a target, mirroring `onEditTargets == nil`; the
  daily-target row additionally collapses under ED-safe with the stat card.
- **Route exports**: both route files default-export only the screen; no tests under `src/app`;
  the routes are the only files importing `getDataEnvironment`, `getSessionStore`,
  `notifyLocalMutation`. Since the rework, `app/settings.tsx` also takes the reset flow from
  `useAppEnvironment()` (`resetLocalData`) and no longer imports `getSyncRuntime`.
- **Test-tooling notes** (for the next unit): RNTL 14.1's `render` is async (`await render(...)`);
  RN `Switch` needs `fireEvent(el, 'valueChange', value)` wrapped in `act`; `WheelField` selection
  fires through `momentumScrollEnd` with the full nativeEvent shape (see its design test);
  `screen.toJSON()` is the reliable testID sweep (no `findAll` on the v14 root).
