# U-85 The sync store keeps the local fields of an entry it wrote itself

Parity rows DB-02 and DB-03 (the outbox, the sync merge and the engine). Base: `main` 1482777.
Branch `rn/u-85-sync-loser-path`. The API, the wire contract, the schema and the engine's numbers
(batch 50, debounce 500 ms, quarantine at 5 attempts) are untouched.

## The defect, as the tests reproduce it

Two pending upserts of one record travel as two wire operations built from the SAME mirror row
(`outboxEntryForRow` → `mealForOp`: an op has no payload of its own), so both carry the same meal and
the same `updatedAt`. The API (and `FakeServer`) applies the first and answers the second as a loser:
`meal.updatedAt > stored.updatedAt` is false against the record the first op just stored. The loser's
acknowledgement goes through `applyAcknowledgedRecord`, which, because `acceptedOpId` is not the op's
own id, deletes the op and calls `applyPulledRow(..., { force: true })`; `applyPushAcks` then rewrites the
detail row with `detailForMeal(..., 'sync')`: grams, confidence and scan id become null, source becomes
`'sync'`. Text and macros stay right, so the loss is silent.

The reachable shapes: a write followed by an edit inside the 500 ms debounce, any two writes while the
device is offline or in a retry backlog, a save followed by a change of its meal, and
log → delete → log-again with the same id before the first dispatch (the undo of PR 37 re-logs the id).

## The fix: at dispatch, one op per record (candidate 1)

`dueOperations` in `store.sqlite.ts` calls `dropSupersededOperations` before it reads the batch. For every
record that has more than one pending op that is not quarantined, only the newest op (highest `rowid`:
insertion order, so a clock that stood still or went back cannot reorder it) stays; the older ones are
deleted in one transaction. The newest op that decodes is the survivor: a quarantined row is never touched
(it is a dead letter the person can see) and an undecodable newest row keeps its poison path without
costing a valid older op its place. No transaction is taken when no record has two ops.

Why this place:

- An op has no payload. `mealForOp` rebuilds every upsert from the current mirror row, so the newest op
  already says everything an older one says; the older ones add only an `opId` and a second wire copy of
  the same meal, whose only effect is to be answered as a loser against its own sibling. The cure of the
  false loss is not to create it.
- The collapse covers the whole outbox, not the batch window and not the due set. That is why it also
  closes the cases a batch-local rule would miss: the sibling in the next batch of 50, the older op that
  sits in a retry backlog, the older op that waits for its retry time (S3).
- The merge keeps its contract untouched: `applyAcknowledgedRecord`, the `force` path and the pending
  intent skip of `applyPulledRow` do not change a line (P1 and P2 pin them, and the older store test
  "an ack with a newer pending op leaves the mirror alone" still passes: the legitimate `kept` case is an
  edit that lands while a push is in flight, which this fix does not touch).

## Candidate rejected: at the acknowledgement

"A losing op whose record was accepted in the same batch is not a loss against another device" was
rejected because:

1. It recognises the sibling only inside one batch (answer carries a sibling op id of THIS batch). A
   sibling acknowledged in an earlier batch, an earlier dispatch, or a batch of 50 that split the two
   ops, still looks like another device and still clobbers the detail row. The rule needs a ledger of
   own acknowledged op ids to be complete, and there is none (schema change, out of scope).
2. It is not enough alone (read from the code, not run as a prototype). The first op of the pair is answered `kept` (the second is still pending when
   it is applied), so the mirror is never stamped with the server's version; the pull of the same dispatch
   then sees a newer remote version, applies it and `applyPullPage` rebuilds the detail row from the wire
   again. The acknowledgement would also have to stamp the sibling's version, which is a second change in
   the merge contract.
3. It keeps sending the redundant op (a push, a ledger row on the server, one more round of validation of
   the exact acknowledgement set) only to throw its answer away, and it makes the rule depend on the
   server's wording (`acceptedOpId` of a sibling) instead of on what the client knows by itself.

The third way (changing what the server answers) is out of scope as the brief says.

## Other things seen, not changed (outside the scope or not part of this defect)

- `applyPullPage` and `applyPushAcks` (the loser path against another device) rebuild the detail row from
  the wire (`source 'sync'`, grams and confidence null) for a record another device won. That is the
  intended mirror of the winner (P2), but it also drops the local-only fields for an entry the user scanned
  on this device and that another device edited later. The wire carries no grams, so there is nothing to
  keep; a decision for the owner if it matters.
- `InMemorySyncStore.dueOperations` (a Jest test double) does not collapse ops per record; the engine tests
  that use it do not write one record twice. The SQLite store is the one that ships.
- The `SyncStore` interface comment of `recordUpsert`/`dueOperations` was updated (one line in `types.ts`).
