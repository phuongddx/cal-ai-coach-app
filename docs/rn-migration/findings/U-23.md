# U-23 findings: sync engine, session wiring and triggers

Unit of `docs/rn-migration/plan.md`. Worker: Worker-S1. Branch `rn/u-23-sync-engine`. Parity rows PL-04, NW-02, DB-02, DB-03,
CO-07 (detail in `docs/rn-migration/parity-detail/sync.md`). JS only; no native build, no Simulator.

## What was built

- **A. Random ids.** `data/sync/uuid.ts` takes its 16 bytes from `expo-crypto` `getRandomValues` through a lazy `require`
  (same loading style as `data/auth/appleNonce.ts`). No fallback: when the secure source fails, `newUuid` throws. The Jest
  mock `__mocks__/expo-crypto.ts` has `getRandomValues`. `grep -n "Math.random" apps/mobile/src/data/sync/uuid.ts` and
  `grep -rn "crypto.randomUUID" apps/mobile/src` print nothing.
- **B. An acknowledgement applies the record.** `applyAcknowledgedRecord` in `repos/syncMergeRepository.ts`, used by
  `store.sqlite.ts` `applyPushAcks`. The op always leaves the outbox. A newer pending op on the record: mirror untouched.
  Winning op (`acceptedOpId` is its own id): local content stays, version stamped (the Swift rule). Losing op: the returned
  record is written like a pulled row, **forced** even when its version is not newer than the mirror (see decision 1).
- **C. One writer at a time.** `repos/sqlDb.ts` `inTransaction` runs on a per-handle promise chain; a failed call rolls back only
  its own transaction and the next call still runs.
- **D. The engine.** `data/sync/engine.ts` ports `SyncEngine.swift`: generation tokens, 500 ms trailing debounce with a
  trailing rerun, FIFO batches of 50, `stop()`/`bind()` drain barrier, quarantine at 5 attempts, exact ack set through
  `validateAcknowledgementSet`, pull pages until `hasMore` is false with `validatePullResponse` on each page (contract rows
  `{seq, record}` mapped to the shape the core validator takes), the error sink with `poisonedOperations`, `DispatchResult`.
  `backoff.ts` is `Backoff.swift` (1, 2, 4, 8, 16, 30, 30 s). `triggerSeams.ts` has the three seams, `triggers.ts` wires them
  to AppState, NetInfo and local writes. Twins of the five Swift test files: see the table in the parity detail.
  `testing/engineHarness.ts` is the Swift `makeHarness`/`MockTransport` on a fresh sql.js database.
- **E. The session user.** `data/sync/runtime.ts` builds the transport with the session store's token provider and refresh
  (`getSessionStore()`), binds the engine to the session user on sign-in (and restore at launch), stops it on sign-out,
  rebinds on a user change. Mirror rows carry the session user id (`createSqliteSyncStore(db, {ownerId})`). `LOCAL_OWNER_ID`
  and `DEMO_USER_ID` apply only when there is no session. Without a session the engine makes no request and reports
  `unauthorized` (`sync/runtime.session.test.ts`, six cases).
- **F. End to end.** `scripts/rn/e2e-sync.sh` fixed for the global version sequence (A is numbered first, C is the next number, cursor is C's version: 1, 2, 2 on a fresh cluster; the Jest integration suite deletes its dev-user rows afterwards, so the script also passes after `npm test` on the same cluster)
  and it runs green on a fresh cluster. `sync/e2e.integration.test.ts` runs the real engine and SQLite store (sql.js) for two
  devices against the API on 8787: convergence, tombstone, conflict loser. `scripts/rn/e2e-sync-app.sh` is repointed to
  `diary_entries`, `diary_entry_details`, `pending_ops` and `sync_state`.

## Decisions the owner should know about

1. **Force-apply of the returned record on a losing ack.** The server does not number a losing op: it answers `applied` with the
   winner's record. If the mirror already holds a version at least as new (an earlier pull), skipping the record would keep the
   loser's rejected text under the winner's version for good. So the ack writes the record unconditionally (test: `a losing ack
   applies the server record even when its version is not newer than the mirror`). Only when no other op is pending for the record.
2. **A 400 quarantines the whole batch at once**, without waiting for 5 attempts: the server rejects a malformed batch
   deterministically, and the batch cannot be told apart. The engine rethrows `SyncError('invalidRequest', {details:{quarantined:true}})`.
3. **Risk to decide: quarantine after 5 attempts counts transport errors.** The brief (and Swift) count them, so a device on a
   flaky network for 5 dispatches dead-letters ops that were fine; they leave the push loop and stay local. Swift has the same
   behavior. A reset button or a "retry quarantined" action does not exist yet.
4. **Pull pages until `hasMore` is false.** Swift pulls one page per dispatch. The RN wire has `hasMore`, the brief asks for it.
5. **Naming.** The network trigger is `NetworkTrigger` (Swift `NWPathTrigger`), rising edge only. `BGTaskTrigger` takes a submit
   seam; no consumer (expo-background-task) is wired in this unit.
6. **Transport errors surface wrapped.** A non-`SyncError` thrown by a transport reaches the caller as `SyncError('transport', {cause})`.
7. **Injected clock vs real clock.** The Swift `OutboxRepository.dueOps` compares retry times with the real `Date()`, not the
   injected clock. RN uses the injected `now`, so the twin of the dead-letter test clears the retry time before replaying
   (`clearRetryTime`), and the harness `schedule` is a no-op (Swift has no retry timer; the retry waits for the next trigger).
8. **Debug token is opt-in.** Without a session the runtime sends nothing, unless `extra.apiToken` is set in the app config
   (`Constants.expoConfig.extra`): then it uses that token and `LOCAL_OWNER_ID`. This keeps the spike console and the app-driven
   e2e script working. The runtime reads no built-in token (the `syncClient` default provider still falls back to the spike dev token when a caller passes none).
9. **On sign-in the engine runs one `sync()`** right after `bind`, so a user who just signed in does not wait for the next trigger.
10. **Store and engine extras.** `OutboxEntry.nextRetryAt`, `UndecodableOperation`, `DueBatch`, `dueOperations` and
    `markAttempts(opIds, lastError, retryAt)` were added to the store port; `inMemorySyncStore.ts` and `fakeServer.ts` follow
    (the fake server now numbers from one global sequence like the real SQL).

## Replaced or changed existing engine tests (14 existed)

All 14 still pass; none was deleted. One line per change:
- All 12 cases of `engine.test.ts` and the first of `engineChange.test.ts`: the harness is async and calls `engine.bind(OWNER)`, because an unbound engine now answers `unauthorized`.
- `applying the same pull page twice changes nothing`: first cursor expectation 1 became 2 (the page cursor is the seeded record's global version).
- `a crash while applying a pull page rolls the cursor and the writes back together`: cursor expectation 1 became 4, same reason.
- `a sync already running coalesces into one follow-up run`: the two `await Promise.resolve()` became a bounded loop that waits for the second push (the engine has more awaits per run).
- `a new engine over the same store drains what a previous run left`: the second engine is bound to the owner.

## What Swift does to the local store on sign-out and account deletion (for U-51)

`AppEnvironment.performLocalAccountReset()`: best-effort `accountDeletionTransport.deleteAccount()`, then `authSessionStore.signOut()`
(unconditional, so a surviving Keychain session cannot re-authenticate on the next launch), clears `authSession`, removes the
ED-safe and burn-add-back defaults, then in one write deletes every row of every table except `grdb_migrations` and sqlite
internals. It does not call `syncEngine.stop()`; the engine is rebound by `handleSignIn` / `restoreSession`. A plain sign-out
that is not an account reset is not a separate path in `AppEnvironment.swift`. RN: the runtime stops the engine when the session
clears and keeps the local rows; the table reset itself is U-51 (not done here).

## Not verified

- `scripts/rn/e2e-sync-app.sh` was repointed but **not run**: no Simulator in this unit. The replay body it builds from
  `pending_ops` + `diary_entries` + `diary_entry_details` is the most likely place for a mismatch; a rejected body fails step 4 loudly.
- Hermes behavior of `expo-crypto` `getRandomValues` on a device (Jest uses the mock); the lazy `require` path on a native build that
  predates the package.
- NetInfo/AppState/background-task behavior on a device; triggers are tested through their seams.
- The integration suite uses a node:http `fetch` because jest-expo's global `fetch` has no network; the production path uses RN's `fetch`.
- `scripts/rn/e2e-sync.sh` is not re-runnable for user 1 on the same cluster (fixed opIds answer `duplicate`): run `start-api.sh stop` and `start-api.sh` first (stated in its header).
