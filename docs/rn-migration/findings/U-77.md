## 1. Needs a design component

1. **`BannerNote` lacks caution/error variants** (`src/design/components/BannerNote.tsx` exports
   `success | neutral | info`). The failed-export row (frames `x-write-*`, error tint) and the
   goal-floor card (frame `p-target-floor`, caution tint) need them. Held locally for now:
   `features/profile/StateNote.tsx`, token-only (`cautionTint`/`cautionInk`,
   `errorTint`/`errorInk`), bold lead via the exported `markdownSegments`. A design variant
   replaces the file.
2. **`SettingsRow` has no chevron-off option.** The frame's rule "rows without an action lose
   their chevron" cannot be expressed; the inert Units row still renders the chevron. Feature-side
   the row stays a `SettingsRow` (identifier/label/value parity intact); a `chevron?: boolean`
   prop on the design component is the fix.
3. **`SettingsRow` value has no semantic-color option.** The frame's "Connected" value is
   `successInk`; the component renders every value `text2`. The value string is correct; the tint
   needs a design prop.
4. **`SecondaryButton` has no disabled visual variant** (findings/U-71.md open question). The two
   billing buttons are disabled (`accessibilityState.disabled`, no `action`) and the screen wraps
   each in a dimmed, `pointerEvents="none"` view — a `disabled` prop with the pressed-off opacity
   belongs in the component. (The design-system handoff also asks for `action` to become required
   once every caller passes one; both billing buttons still render without one, so the prop stays
   optional.)
5. **Skeleton price slots.** The loading paywall (frame `b-paywall-loading`) draws fill-colored
   bars from plain token Views. A `Skeleton` component would standardize them.

## 2. Deviations

1. **No kg / lb switch on Profile** (brief decision). The frame's Units segment is app-wide unit
   conversion — a new feature neither app has. The row shows the unit ("Metric") and stays inert.
2. **`profile.stat.daysLogged` removed** (brief decision, recorded): the frame's third stat is the
   goal weight (`profile.stat.goalWeight`, new). The stats query still computes the 30-day count
   (route SQL unchanged); the card no longer renders it.
3. **Plan line stays "Free · Since <month> <year>"** — "Plus · renews <date>" waits for the store
   (follow-up, store). The session contract (`SessionUserSchema`) carries `id`, `email`,
   `providers` — **no display-name field**, so the account name is the e-mail address (the
   display-name-if-given rule degrades to the e-mail; a profile name field is a backend
   follow-up). Signed-out (demo) the name renders an em dash, never a hard-coded name.
4. **Apple Health status is a synchronous read** of the step type's authorization
   (`authorizationStatusFor`, route-level per the U-42 convention), mapped
   `sharingAuthorized → "Connected"`, everything else → "Not connected"; a device without the
   native module reads as not connected. The row's value has no success tint (see design gap 3).
   `profile.healthNote` still reveals on tap.
5. **Profile rows the frame does not draw were removed**: the inert "Reminders Off" and
   "Appearance System" rows (no identifiers existed for either) and the "Preferences"/
   "Integrations" section headers (frame: "Plan", "App"). Health + Units now share the "App" group.
6. **Subscription card shows the plan but not the scan limit** (the acceptance wording asked for
   "the plan and the scan limit from the entitlement state"). No RN module keeps a stored
   entitlement — the only scan-limit value in the client is the scan flow's transient 402 fallback
   (`scanModel.ts`, not exported, and `features/scan` is outside this unit's scope) — so the card
   renders "Free plan" and no number. Follow-up: a stored entitlement read (backend/store) feeds
   both the limit line and "Plus · renews …".
7. **No "Active" badge on a Free plan** (the frame's badge assumes a subscription) and the
   frame's "Billing history · Restore purchases" ghost row is not drawn (brief decision).
   `settings.billingNote` now reads "Plans are not available in this build." (the frame's note is
   store-dependent; this one says why the buttons are inert).
8. **ED-Safe subtitle keeps today's copy** (brief decision; U-78 wires widgets and the Live
   Activity). The burned add-back subtitle already states its effect; its IN-01 note stays because
   the toggle still has no consumer (PL-13).
9. **Export range chips not built.** The `x-*` frames draw an "Export diary" sheet with Last 7
   days / Last 30 days / All time; the RN export is a full export (`buildFullExportCSV`) with no
   range concept, and the brief binds the tap to `exportCsvAndShare` from the Settings row. The
   three states render as rows under the export row, per the brief's decisions. A range-scoped
   export is a follow-up if the owner wants the sheet.
10. **Target sheet keeps today's controls.** The frames' current-weight card (with the Apple
    Health attribution and Update action), pace options (0.25/0.5/0.75) and the live ember card
    are not built: the sheet never edited pace (no new feature, standing order 16), `UserTarget`
    carries no age so `TargetsEngine.bmr` cannot recompute live without inventing data, and the
    weight-log/Health read is outside the unit. The frame's goal control (typed field + stepper +
    ruler) would also replace the wheel — the wheel stays (today's logic, DS identifiers
    `wheel-*:Goal weight` intact). Follow-ups: pace editing, a live target recompute (needs age on
    the target), the ruler-based goal control.
11. **Goal-floor card uses the engine's flat minimum** (owner's correction): `TargetsEngine`
    clamps to `minGoalWeightKg` (40) and computes no height-based healthy range, so the card
    (frame `p-target-floor`) names the engine's clamped value without any height claim and never
    says "BMI" (`goalFloorCopy`). The save button names the clamped value ("Save 40 kg goal").
    Reachability: the wheel's own range is 40…150, so a sub-floor goal only arrives from stored
    data (the model does not sanitize its initial — the card catches it). Follow-up (engine): a
    height-based healthy floor (`healthyGoalFloorKg(heightCm)`, BMI 18.5 without the name in copy)
    turns the frame's card into a live guardrail.
12. **Paywall/cancel dates and prices**: no price, trial term or expiry date appears anywhere —
    the canvas values are placeholders (D13). The failed state's caution card, "Price unavailable"
    options and disabled CTA follow `b-paywall-failed`; the ready state renders only store-sourced
    strings. The cancel flow's first check row says "until the end of the period you paid for"
    (`{expiryDate}` has no source) and the Apple note says "subscriptions page", not "sheet"
    (decision D14: `Linking.openURL('https://apps.apple.com/account/subscriptions')`, no native
    module). "Photo scans drop to 3 a week" keeps the frame copy — the free limit of 3 is the
    server's documented free entitlement (the 402 envelope's `scanLimit`).
13. **Terms · Privacy render as plain text** — no URLs exist in the app for them yet.
14. **`_layout.tsx` not edited** (outside the writable scope): `plans.tsx` and `cancel-flow.tsx`
    rely on expo-router registering every file under `src/app` as a stack screen; the explicit
    `Stack.Screen` entries only customize options, so the two routes push with the stack defaults
    (no header, `headerShown: false` is global). If the owner wants `presentation: 'formSheet'` on
    `plans`, that is a one-line `_layout` entry.

## 5. Port decisions

- **The share dismissal** (brief: read the typings first): `expo-sharing`'s `shareAsync` resolves
  `Promise<void>` — it cannot report a dismissal — so the route's share port is RN `Share.share`
  (`node_modules/react-native/Libraries/Share/Share.js`: resolves
  `{ action: 'sharedAction' | 'dismissedAction' }`, dismissal on iOS is `dismissedAction`; `url`
  is the iOS file field). The route wraps `exportCsvAndShare` and maps the captured action to
  `'shared' | 'cancelled'` for the model. Opening Settings still only prepares the file
  (`prepareCsvExport`).
- **The empty export** is detected from the prepared text (`hasExportRows`): the generator writes
  a `# <table>` line per table and emits the header/rows only when a row exists, so an empty
  diary is comment-and-blank lines only.
- **The paywall model** is store-shaped (`loadOptions`/`restore`/`purchase` injected) and the
  route injects a loader that always rejects — the screen always ends in the failed state, exactly
  the brief's "no store is connected". The shell (hero, feature rows, option cards, Restore/Close,
  terms note) is identical across states.
- **The cancel flow** needs no model: two injected callbacks (`onContinue` → `Linking` in the
  route, `onKeep` → `router.back()`), like `ProfileView`'s props-driven seam.
- **`_layout.tsx` untouched** (deviation 14) — the routes rely on expo-router's file-based
  registration; `routes.test.tsx` proves both deep links against the real file list.
