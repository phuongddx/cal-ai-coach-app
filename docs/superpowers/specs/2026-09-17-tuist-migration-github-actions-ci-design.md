# Tuist Migration + GitHub Actions CI — Design

Status: approved (in-chat), pending written-spec review
Date: 2026-09-17

## Goal

Replace XcodeGen with Tuist as the `native/` project generator, and add GitHub
Actions CI that verifies the build/tests on every push/PR — replacing "build
locally to check it still works" with an automated, repeatable check.

## Context

- `native/` is a native SwiftUI app (iOS 18 floor, Xcode 26.x / Swift 6),
  currently generated by XcodeGen 2.46.0 from `native/project.yml`.
- 5 local modules (`CoachCalCore`, `CoachCalNetworking`, `CoachCalPersistence`,
  `CoachCalSync`, `CoachCalDesignSystem`) are already real SwiftPM packages
  under `native/Modules/*/Package.swift` — Tuist can consume these via
  `.package(path:)` without converting them into Tuist targets.
- Tuist 4.206.0 is already installed locally (`/opt/homebrew/bin/tuist`).
- No `.github/` directory exists yet. The only existing CI is Xcode Cloud's
  `ci_scripts/ci_post_clone.sh`, which does: install xcodegen → `xcodegen
  generate` → `swift test` per module (skipping `CoachCalDesignSystem`, which
  has no macOS platform) → `xcodebuild test` against a simulator.
- `native/project.yml` hardcodes Manual code signing (`DEVELOPMENT_TEAM`,
  a distribution `CODE_SIGN_IDENTITY`, `PROVISIONING_PROFILE_SPECIFIER`) for
  the real device/TestFlight build path.
- Prior research (this session) established: (1) neither XcodeGen nor Tuist
  currently emit the newest native Xcode project format
  (`objectVersion = 100` / Xcode 26.3-era) — this migration does not change
  that fact and is not attempting to fix it; (2) GitHub-hosted `macos-26`
  runners include Xcode 26.6, matching the local toolchain.

## Scope

**In scope:**
1. Replace `native/project.yml` (XcodeGen) with Tuist manifests.
2. Update Xcode Cloud's `ci_scripts/ci_post_clone.sh` to generate via Tuist
   instead of XcodeGen (required for Xcode Cloud builds to keep working —
   not optional, since `project.yml` is being deleted).
3. Add `.github/workflows/ci.yml` — build/test verification via Tuist, on
   the iOS Simulator, unsigned.

**Out of scope (explicitly not doing):**
- Changing `objectVersion` / chasing the newest raw pbxproj format.
- Converting the 5 local SwiftPM modules into Tuist-native targets — they
  stay as plain SwiftPM packages, referenced via `.package(path:)`.
- Retiring Xcode Cloud or changing the real signed TestFlight/App Store
  build pipeline — GitHub Actions CI is a build-verification addition, not
  a replacement for release builds.
- Any change to `App/Features/**`, `App/CoachCal/**`, module `Sources/`/
  `Tests/`, entitlements, or `PrivacyInfo.xcprivacy`.

## Design

### 1. Tuist manifests (new)

- `native/Tuist.swift` — project-wide Tuist config (Swift tools version,
  compatible platforms).
- `native/Tuist/Package.swift` — external SPM dependencies currently listed
  in `project.yml`'s `packages:` block: `Sentry` (9.28.0 exact),
  `PostHog` (3.75.2 exact), `ViewInspector` (0.10.3 exact, test-only),
  `SnapshotTesting` (from 1.19.4, test-only).
- `native/Project.swift` — replaces `project.yml`'s `targets:` block:
  - `CoachCal` app target: sources `App/CoachCal` + `App/Features`,
    dependencies on the 5 local packages (via `.package(path: "Modules/...")`)
    + `Sentry` + `PostHog` + the `CoachCalWidget` extension target, Info.plist
    properties (camera/health usage strings, `NSSupportsLiveActivities`, the
    `coachcal://` URL scheme, env-var-backed keys) carried over verbatim,
    `CODE_SIGN_ENTITLEMENTS` pointing at the existing
    `SupportingFiles/CoachCal.entitlements`, bundle id `com.nextlabs.coachcal`.
  - `CoachCalWidget` extension target: sources `CoachCalWidget/`.
  - `CoachCalTests` / `CoachCalUITests` targets: sources + `ViewInspector`/
    `SnapshotTesting` test dependencies, mirroring current XcodeGen test
    target wiring.
  - Manual signing settings (`DEVELOPMENT_TEAM`, `CODE_SIGN_IDENTITY`,
    `PROVISIONING_PROFILE_SPECIFIER`) preserved as-is for the app target,
    since Xcode Cloud still needs them for signed builds.

### 2. Xcode Cloud script update

`ci_scripts/ci_post_clone.sh` changes:
- Replace the `xcodegen`-install-and-generate block with a Tuist
  install-and-generate block (`curl -Ls https://install.tuist.io | bash` or
  `mise`/`brew install tuist`, then `tuist install && tuist generate
  --no-open`), pinned to 4.206.0 to match local.
- Per-module `swift test` loop and the final `xcodebuild test` invocation
  are unchanged (they don't care which generator produced the `.xcodeproj`).

### 3. GitHub Actions workflow (new)

`.github/workflows/ci.yml`:
- **Triggers:** `push` (any branch), `pull_request`, `workflow_dispatch`.
- **Runner:** `macos-26`, then `sudo xcode-select -s
  /Applications/Xcode_26.6.app` to pin the exact toolchain.
- **Steps:**
  1. Checkout.
  2. Install Tuist 4.206.0 (pinned, matching local + Xcode Cloud).
  3. `cd native && tuist install` (resolve deps).
  4. `tuist generate --no-open`.
  5. Per-module `swift test` loop (same skip-list as
     `ci_post_clone.sh`: skip `CoachCalDesignSystem`, no macOS platform).
  6. `xcodebuild test -scheme CoachCal -destination "$destination"
     CODE_SIGNING_ALLOWED=NO`, where `$destination` is resolved the same
     way `ci_post_clone.sh` already does (query `xcrun simctl list devices
     available` for the first available iPhone, falling back to a fixed
     name if none found) — not hardcoded, to avoid breaking when the
     GitHub-hosted runner's default simulator set shifts. Unsigned because
     this is build/test verification only, not a release artifact; avoids
     needing certs/provisioning-profile secrets in GitHub.
- **Caching:** cache `native/.tuist` / SPM checkouts keyed on
  `native/Tuist/Package.resolved` to avoid a full dependency re-fetch every
  run.

### 4. Cutover / removal

- Delete `native/project.yml`.
- `native/CoachCal.xcodeproj` stays gitignored (regenerated by `tuist
  generate`, same as it was regenerated by `xcodegen generate` before).
- `native/Package.resolved` (XcodeGen-managed, repo root of `native/`) is
  removed; Tuist manages its own resolution under `native/Tuist/` /
  `.tuist/`.

## Validation

Before treating the migration as done:
1. Run `tuist install && tuist generate --no-open` locally once, then the
   full `xcodebuild test` command from the new CI step — this is the one
   local build that proves the manifests are correct, not a substitute for
   CI on every future change.
2. Confirm all 5 module `swift test` suites still pass unchanged (they
   don't depend on the generator).
3. Push a branch and confirm `.github/workflows/ci.yml` goes green on
   GitHub Actions.
4. Confirm Xcode Cloud's `ci_post_clone.sh` still succeeds with the Tuist
   swap (can only be verified via an actual Xcode Cloud run, which requires
   a push — flagged as a real risk, see below).

## Risks / open items

- **Xcode Cloud verification is not fully verifiable ahead of a real Xcode
  Cloud build.** The `ci_post_clone.sh` Tuist swap is a best-effort
  translation; if Xcode Cloud's environment lacks something the local/GitHub
  Actions Tuist install has (e.g. a different install method needed in that
  sandboxed environment), it may need a follow-up fix after the first
  Xcode Cloud run post-migration.
- **Dependency resolution differences:** Tuist and XcodeGen/SPM may resolve
  transitive versions slightly differently even with the same `.exact()`
  pins on direct dependencies (e.g. Sentry's/PostHog's own sub-dependencies).
  Not expected to cause issues given all direct pins are exact, but worth
  a diff-check of `Tuist/Package.resolved` vs. the old `Package.resolved`
  after first generate.
- **GitHub Actions macOS runner cost/minutes:** `macos-26` runners are the
  most expensive GitHub-hosted runner tier; not addressed here since no
  budget constraint was stated, but worth knowing before merging.
